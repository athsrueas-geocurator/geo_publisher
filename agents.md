## Publishing workflow and current scope

- **User requirement: one pilot for a new content pattern, then one large proposal.** When publishing a new kind of content or materially changed schema/rendering pattern, publish one representative example and verify its execution, indexed fields/links and actual rendering. Once it passes, consolidate all remaining compatible related content in the destination space into one proposal and vote once. Reuse prior verified pilot evidence for unchanged patterns; do not repeat pilots per record, study or script. Include entities, properties, citations, blocks, tables, memberships, schema additions and internal links together, allocating persistent IDs up front. Do not publish remaining rows or components one at a time for agent convenience.
- Local research, validation, API reads and preparation may use small batches; these are not governance proposal boundaries. Combine compatible reviewed work into one hash-bound payload and one journal. Keep different studies/model kinds in separate tables where required, but those tables can share a proposal. Never concatenate old submitted payloads or bypass their semantic checks.
- Beyond the justified pilot, split publication only for a concrete boundary: different destination spaces/governance, a verified payload/transaction limit, an unavoidable external dependency, genuinely unreviewed/blocked content, or the user's explicit request. Record why consolidation cannot work and the smallest necessary number of proposals before signing. A tool supporting only one small package is an engineering limitation to fix, not permission for dozens of votes. Follow both the Geo Explorers one-example rendering check and the user's consolidation requirement. See [consolidated proposal procedure](docs/publisher-reliability-review.md#consolidated-proposals--user-requirement).

- Generate public entity links with `geoEntityUrl` in `src/publication-evidence.ts`: `/space/{spaceId}/{entityId}`. Do not invent `/entity/{id}` links. API indexing and rendered acceptance are separate checks; open the exact shared URL before announcing a page as live. A broken route is not a reason to republish or vote again.
- Preserve all prior journal evidence when recording later milestones, including edit ID, CID, stable block IDs and transaction hash. Persist `submitting` before sending; any uncertain submission requires reconciliation, never a blind retry. The personal quiz verifier is `bun scripts/verify-knowledge-gap-quiz.ts`.
- A request to draft a Discord post in a code block means prepare copy in chat; do not inspect Discord or send it unless explicitly asked. Use the verified space-scoped URL in the copy. Verify UI creation instructions against the actual editor before presenting exact controls. Plain Markdown headings are text blocks, not proof of interactive cards.
- For requested Git pushes, use ordinary Git from this repository, preferably `powershell -NoProfile -File scripts/push-noninteractive.ps1`. It disables terminal and credential-manager prompts for that invocation. Do not invoke `gh auth login`, open an account picker, change credential stores, or retry interactively after an authentication failure. Keep commits scoped when unrelated changes are present.

- Human operators start with `bun run publisher` or `publisher.ps1`; see [the human CLI guide](docs/human-publisher-cli.md). Maintain the CLI and its tests when changing shared gates. Do not add bypass flags or automatically accept source/identity/content judgments. Discovery and inspection must remain usable without signing credentials.
- Start queue work with `publisher.ps1 queue`, then filter package candidates with `publisher.ps1 list --status pending`. Pending includes holds and historical attempts, not signing approval. A legacy CLI limitation must never trigger recreation of an executed entity/package. Local snapshot assessments cannot establish live readiness after later repairs; consult receipts and fresh scoped reads.

Use [publishing_queue.md](publishing_queue.md) for current work and domain notes for source evidence. Historical pause and prepare-only statements are dated snapshots, not current authorization.

- Read [the operator procedure](docs/publisher-reliability-review.md#short-operator-procedure-for-a-simpler-agent), applicable design documents and [the handoff](docs/education-initiatives-handoff.md). Never interpret an existing draft as approval or proof of source accuracy.

- For code-only audits, do not publish to Geo or run destructive reset/blanking scripts. User authorization persists; skill templates do not require asking again for already authorized work.

## Follow the design documentation

- Always read and follow the applicable design documentation before preparing or publishing content, changing page layouts, or implementing dashboard behavior. Treat the documented design as an acceptance requirement; do not substitute personal assumptions or whatever happens to render.
- Known local references: [GeoBrowser content policy](docs/geobrowser-content-policy.md), [Education description guidelines](docs/education-description-guidelines.md), [numeric formatting findings](docs/geo-number-formatting.md), [dashboard data contract](docs/education-dashboard-data-contract.md), and [publishing handoff](docs/education-initiatives-handoff.md). Follow their source links and any user-supplied design references relevant to the work. These local notes are not proof that every governing design document has been identified.
- If the applicable design docs cannot be located or it is unclear which documents the user means, ask the user for the links before making design-dependent decisions. Continue independent work that does not depend on the missing guidance. Once supplied, record the links here or in the relevant folder's guidance so future work uses them.
- Verify the actual rendered result against the applicable design, including description length, content-block placement, table organization, numeric formatting, and citations. Record any mismatch and fix it before claiming design compliance. Explicit user corrections take precedence over older local notes.

Update an existing relevant file rather than creating duplicate notes; otherwise create a clearly named Markdown file.

## Geo read diagnosis before import or repair

Read [geo-api-diagnosis.md](docs/geo-api-diagnosis.md) before interpreting empty discovery, changing read helpers or preparing a missing-data repair. Follow its September 14 consumer checklist. Root `entitiesConnection` accepts `spaceId`/`typeId`; `EntityFilter` instead exposes `spaceIds`/`typeIds` with `anyEqualTo`. Relation and value filters retain their own `spaceId` fields. Never perform a global field-name replacement.

Do not turn HTTP-200 GraphQL errors, timeouts, invalid response shapes, failed cursor pages or bounded/ranked searches into zero matches or permission to create entities. Use complete small cursor pages, ID hydration and direct scoped edge checks; preserve timestamps and exact query evidence. For the documented Saga discrepancy, use passing table-specific/collection reads and retain source, trial, follow-up and estimand partitions. Record conflicting read paths as unresolved rather than recreating existing edges. Apply current user authorization and the bounded publication gates above.
